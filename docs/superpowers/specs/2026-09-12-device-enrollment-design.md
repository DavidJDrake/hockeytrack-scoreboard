# Device Enrollment and the Admin Site — Design

**Status:** accepted
**Date:** 2026-09-12
**Scope:** sub-project A of three (see the device image design, §3). How a
stranger's freshly flashed panel earns its own AWS IoT certificate, bound to an
owner, with nobody provisioning it by hand — and the site that binds it.

## 1. Purpose

Today every scoreboard must be provisioned by the project owner, from a machine
with administrator credentials, by running `tools/provision.sh` and copying the
resulting private key onto the device's SD card by hand. That is workable for
one panel on one desk. It is not a product, and it is the single thing standing
between this project and "download an image, flash it, and it works."

This design removes the manual step. A panel generates its own key, asks to be
enrolled, shows a code, and becomes a working device the moment someone who
owns an account types that code into the website.

It also resolves **SCO-8** ("Fleet management: decide before the second device
leaves the house"), which is this question in ticket form.

## 2. Decisions taken before this design

Settled in brainstorming and treated here as fixed inputs.

| Question | Decision |
|---|---|
| Does setup require a keyboard on the Pi? | No. The code travels panel → website, which means a public endpoint |
| Scope | The complete admin site is folded in, not just enrollment |
| Is AWS IoT with per-device X.509 required? | Yes — decided in the image design, unchanged here |
| Who can create an account? | Invite-only. The Cognito pool stays closed; public sign-up remains out of scope |
| How is the certificate issued? | `iot:CreateCertificateFromCsr` — the device keeps its private key |
| Can a shoulder surfer claim a code they read off the screen? | No, when the panel was pre-bound. The owner's name travels on the boot partition, so the code is claimable only by them |

## 3. What this amends in an accepted spec

`docs/superpowers/specs/2026-09-07-admin-site-design.md` is accepted and its
§3.3 specifies pairing already. It does so on an assumption this design breaks,
and the change is deliberate rather than incidental.

That spec says the pairing code is *"derived from the thing name rather than
generated by the device, so that the device still never publishes anything:
provisioning gives each thing a random suffix, and that suffix is the pairing
code."* That works only because it assumes the device was provisioned in
advance. A freshly flashed panel has no thing name, so there is no suffix to
derive a code from.

The same section anticipates this and defers it: *"AWS fleet provisioning's
provisioning by trusted user solves a different half of the same problem — how
a device gets a certificate at all without someone hand-copying a private key.
Pairing and provisioning should be designed together."* This document is that
deferred half.

**Two amendments, both narrow:**

1. **"The device never publishes anything" becomes "the device never publishes
   to the bus."** A panel that must obtain its own certificate has to speak
   before it has one. It makes exactly one outbound HTTPS request in its life —
   the enrollment request — and is subscribe-only on MQTT forever after. The
   exception is confined to a single endpoint that cannot issue anything
   without an authenticated owner.
2. **The pairing code is no longer the thing name's suffix.** They are separate
   values with separate lifetimes, which is what lets a code expire and be
   reissued without renaming a device. This also closes the "provisioning
   suffixes" item in SCO-26.

Everything else in that spec stands: the ownership table, the retained-config
control path, the API-served game list, the hosting shape, and that spec's
own out-of-scope list.

## 4. Facts established by investigation

Recorded with their evidence, because two of them were assumptions until
checked.

1. **Nothing creates a device row today.** `Register(ctx, thingName, code)`
   exists in `cloud/internal/devices/store.go` and no route in
   `cloud/cmd/api/handler.go` calls it; `tools/provision.sh` does not write a
   row either. So the existing `POST /api/devices/claim` has nothing to find.
   The claim half was built; the register half never was.
2. **The admin API's role holds no IoT registration permissions.** Verified
   against the live role `scoreboard-api`: `iot:Publish` and
   `iot:RetainPublish` on `topic/scoreboard/*/config`, and nothing else in IoT.
   Certificate minting is a genuine privilege increase, not a small edit.
3. **The Cognito pool is invite-only and currently holds zero users**
   (`AllowAdminCreateUserOnly: true`, verified live). So no certificate can be
   minted by anyone at all until the owner creates an account for them.
4. **The site's distribution is live** at `scoreboard.davidjdrake.com`, serving
   a holding page over TLS with a CSP that already names the admin API and
   Cognito hosts and nothing else.

## 5. The enrollment flow

1. **First boot, no identity.** The device generates a P-256 keypair and a
   certificate signing request, writes the key to
   `/var/lib/scoreboard/private.pem.key` at mode 600, and keeps both. The
   private key never leaves the SD card.
2. **`POST /api/enroll`**, unauthenticated, carrying the CSR and — if the card
   was prepared with one — an **owner hint**. The server validates the CSR,
   assigns a thing name, a **pairing code** and a **collection token**, and
   writes a pending enrollment row with a TTL. It creates no thing and no
   certificate. It returns the code and the token.
3. **The panel displays the code**, on the "Not registered" screen the device
   image work already built for this purpose.
4. **The owner signs in and types the code.** If the enrollment carries an
   owner hint, the claim is refused unless the signed-in caller is that person.
   Only then does anything get minted: sign the CSR, create the thing, attach
   the principal and the device policy, write the ownership row, and store the
   certificate against the pending record.
5. **`GET /api/enroll`**, bearing the collection token. 202 while unclaimed,
   200 with the certificate, thing name and endpoint once claimed.
6. **The device writes its config and restarts** into the panel it was always
   going to be.

### 5.1 Why the collection token is separate from the pairing code

The code is displayed on a screen in someone's living room. A guest, a window,
a photograph — anyone who can see the panel has the code. If the code also
collected the certificate, then seeing the screen would be enough to take the
device's identity.

The collection token is never displayed, never typed, and never leaves the
device except in its own poll. It is the device's proof that it is the thing
that asked.

### 5.2 The pairing code

Eight characters of Crockford base32, displayed as `XXXX-XXXX`, with `0`, `O`,
`1`, `I` and `L` absent so it cannot be mistyped. Roughly 10¹² combinations
against a claim endpoint that is authenticated, rate-limited per user, and
one-time per code.

**Codes are unique at the moment they are written**, not merely checked for
collision afterwards: a conditional write reserves the code, and a collision
means generating another. A uniqueness property enforced by detection is not a
uniqueness property.

**Codes rotate, and the enrollment outlives them.** These are two different
lifetimes and conflating them was a mistake worth naming: the enrollment — the
CSR and the collection token — lives 24 hours, because a device should not have
to generate a new keypair just because nobody was home. The *code* lives 15
minutes. The device's own poll is what rotates it: `GET /api/enroll` returns a
fresh code once the previous one expires, so the panel updates its display
without doing anything special, and a code photographed off a screen is useless
within the quarter hour.

### 5.3 The owner hint, and why it closes the shoulder-surfing problem

A code shown on a panel can be read by anyone in the room. Rotation shrinks
that window but does not close it, and no amount of entropy helps against
somebody who can simply see the screen.

It closes when the panel knows whose it is **before** it ever shows a code. The
boot partition already carries setup the owner writes at flash time, so it
carries one more line:

    owner=friend@example.com

The device sends that hint with its CSR. The server stores `sha256` of it and,
at claim time, compares it against the caller's `email` or `cognito:username`
claim. A shoulder surfer reading the screen therefore has a code they cannot
use: claiming it requires signing in as the owner, which is the one thing they
cannot do.

Three properties of this worth stating:

- **The hint is not a secret.** It is an email address sitting in plaintext on
  a FAT partition anyone holding the card can read. It is stored hashed for
  consistency with the code and the token, not because a username needs
  protecting.
- **Matching is on `email` or `cognito:username`, never `sub`**, because `sub`
  is a UUID nobody can type into a file. Comparison is case-insensitive and
  whitespace-trimmed, the same normalization the pairing code gets, because
  this is hand-typed too.
- **The hint is optional.** A card prepared without one behaves exactly as
  described above: any invited user may claim it, with short rotating codes.
  This keeps the file from becoming a new way to brick a setup, and gives the
  stronger property to anyone who writes it.

**The site generates the file.** "Add a panel" produces a
`scoreboard-setup.txt` with the owner line already filled in, which the friend
drops onto the boot partition beside their Wi-Fi settings. That is a better
setup story than typing an address by hand, and it means the panel comes up
already knowing whose it is.

**The file is renamed.** The device image work shipped
`/boot/firmware/scoreboard-wifi.txt`; it becomes `scoreboard-setup.txt`, since
a file named for Wi-Fi that carries an owner line is the sort of small
dishonesty that confuses somebody a year later. Nothing has shipped to anyone,
so the rename costs nothing now and cannot be done cheaply later.

## 6. Abuse bounds

**What an anonymous caller can achieve is junk rows, and nothing else.** No
thing, no certificate, no fleet membership, because minting is gated behind an
authenticated invited owner. The bounds are therefore modest by design:

- a stage throttle of its own, 5 rps and 10 burst, separate from the admin
  API's 20/40, so enrollment traffic cannot starve the site;
- a 24-hour TTL on every pending row, enforced by DynamoDB rather than a
  sweeper;
- CSR validation that caps the body size and pins the algorithm to P-256, so
  nobody burns Lambda seconds on a 16384-bit RSA key.

**No WAF, deliberately.** Per-IP rate limiting is the textbook control and it
costs real money every month to defend against an attack whose payoff is a few
dollars of DynamoDB writes. The honest control here is detection: alarm on the
enrollment rate and on claim-failure rate, and add WAF the day an alarm fires
rather than the day someone imagines it might. Recording this as a deliberate
accepted risk rather than an oversight is the point.

## 7. Data model

**A separate table, `scoreboard-enrollments`**, not the devices table.
`scoreboard-devices` is the irreplaceable ownership record — SCO-23 exists
because losing it means every owner loses every panel — and letting anonymous
internet traffic churn writes into it would be a poor trade for one saved
resource.

| Attribute | Purpose |
|---|---|
| `pk` | `sha256(collection token)` — the partition key |
| `code_hash` | `sha256(pairing code)`. Rotates. A companion reservation item keyed `code#<hash>` is what enforces uniqueness and what a lookup follows — DynamoDB cannot enforce uniqueness on an index, but it can refuse a conditional write, and this removes the need for an index at all |
| `code_expires_at` | epoch seconds; when the code rotates, distinct from the row's own TTL |
| `owner_hint_hash` | `sha256` of the normalized owner hint, or absent |
| `csr` | the submitted PEM |
| `thing_name` | assigned by the server at enrollment |
| `status` | `pending` or `ready` |
| `certificate_pem` | written only after a successful claim |
| `owner` | the claiming Cognito subject |
| `expires_at` | epoch seconds, the DynamoDB TTL attribute |

**Both secrets are stored hashed.** The device sends its token, the server
hashes it and looks up; the site sends a code, the server hashes it and queries
the index. A dump of this table therefore yields nobody a usable collection
token and nobody a claimable code. This is the reasoning behind not storing
passwords, applied to two short-lived secrets that would otherwise sit in
plaintext beside the certificates they unlock.

**The row is deleted once the device collects.** After that the certificate
exists in exactly two places — the device and AWS IoT — and nothing in this
system can hand it out again.

**Thing names are assigned server-side**: `scoreboard-` plus twelve random
base32 characters. Uniqueness without collision handling, and nothing in the
CSR influences it.

### 7.1 The failure worth specifying

If the owner claims but the panel never collects — it died, it was unplugged —
the certificate exists, attached to a thing they own, on a panel that will
never connect. The owner sees a device permanently offline. Recovery is to
unbind, which revokes the certificate, after which the panel enrolls afresh.

That makes **SCO-24** (unbinding does not currently revoke) a dependency of
this work rather than a follow-up: the design's own recovery path depends on it.

## 8. The trust boundary, and why enrollment gets its own Lambda

Certificate minting needs `iot:CreateCertificateFromCsr`, `iot:CreateThing`,
`iot:AttachThingPrincipal` and `iot:AttachPolicy`. The existing admin API role
has none of these (§4, finding 2) and should not gain them: every route in that Lambda
is reachable by any signed-in user, and putting fleet-identity creation behind
the same credential as "rename my panel" widens the blast radius of every bug
in it.

**So enrollment is a second Lambda with a second role.** The admin API keeps
its current permissions; the enrollment function gets the four IoT actions and
nothing else.

**Which policy gets attached cannot be constrained in IAM, and an earlier
version of this document said otherwise.** It claimed `iot:AttachPolicy` must
be pinned to the `scoreboard-device` policy ARN, and called that the sharpest
hole in the design. That control does not exist. AWS authorizes `AttachPolicy`
against its *target* -- the certificate -- not against the policy being
attached, so a statement scoped to a policy ARN matches nothing at all. It was
disproved by simulation rather than by reading: pinned to the policy ARN,
`iam simulate-custom-policy` returns `implicitDeny` for attaching to a
certificate; on `cert/*` or `*` it returns `allowed`; and `iot:DeletePolicy`
against a policy ARN returns `allowed`, so policy ARNs do work for the actions
that take them. The original wording would therefore have failed every claim
with AccessDenied *and* never expressed the constraint it promised.

**What actually contains this, honestly stated.** Four things, none of which is
the single hard pin the earlier text implied:

- The policy name is fixed when the issuer is constructed, so no caller and no
  request can choose which policy is attached.
- The enrollment role holds no policy-authoring actions -- no `CreatePolicy`,
  `CreatePolicyVersion` or `SetDefaultPolicyVersion` -- so it cannot write a
  permissive policy to attach.
- `iot:AttachPolicy` is scoped to `cert/*` in this account, which constrains
  what it can attach *to* even though it cannot constrain what it attaches.
- There is currently exactly one IoT policy in the account.

**That last one is a contingency, not a guarantee**, and it is the thing to
watch: if a second, broader IoT policy is ever created here, this role could
attach it, and nothing in IAM would stop that. Anyone adding an IoT policy to
this account needs to know that.

**Nothing is trusted from the CSR.** Not the subject, not the SANs, not any
extension. The thing name is assigned server-side. A CSR is a public key and a
proof of possession; it is not a request for a name.

## 9. The device's side

The state machine this joins already exists: `screen_for(has_identity,
has_network)` and the "Not registered" screen were built by the device image
work and are currently unreachable placeholders waiting for this.

On first boot with no identity and a working network, the device generates its
keypair, posts the CSR, stores the collection token, and shows the code. It
then polls on a slow backoff — a few seconds initially, settling to every
thirty — because the person on the other end is signing into a website, and a
panel that hammers the endpoint while somebody hunts for their password is the
one that trips its own rate limit.

**Three states get screens rather than silence**, because the alternative is a
friend staring at a dead panel with no way to tell whose fault it is:

- **No network** — the existing offline screen.
- **Enrollment rejected or unreachable** — said plainly, with backoff. This
  must not look identical to "nobody has claimed me yet."
- **Waiting to be claimed** — the code, large, with the site's address beneath
  it, and the owner's name when the card carried one. "Waiting for
  friend@example.com" tells the friend their setup file was read, which is
  otherwise invisible until something goes wrong.

**The owner hint comes from the boot partition**, read from
`/boot/firmware/scoreboard-setup.txt` — the same file that carries the Wi-Fi
settings, renamed from `scoreboard-wifi.txt` now that it carries more than
Wi-Fi. An absent or unparseable `owner=` line is not an error; the panel
enrolls without a hint.

**The keypair is generated once and reused across retries.** Regenerating per
attempt would orphan a certificate every time somebody claimed a code the panel
had already given up on.

**The config write is atomic** — temp file then rename. A power cut mid-write
would otherwise leave a half-written `device.json`, and `Config.load` refuses to
start on a corrupt one rather than re-enrolling, which is the correct behavior
and would strand the panel.

## 10. The site

One page does the real work: sign in through Cognito's hosted UI, land on a
list of your panels. The empty state is a single field — type the code from
your screen. That is the entire onboarding interface and it should stay that
small.

The same page produces the setup file. "Add a panel" offers a
`scoreboard-setup.txt` containing the signed-in user's owner line, to be
dropped on the boot partition beside the Wi-Fi settings, so the panel comes up
pre-bound and its code is claimable by nobody else.

Beyond it, v1 is what the accepted admin-site spec already settled: choose a
game per panel, rename a panel, unbind a panel. Nothing else. §7 of that spec
rules out brightness, sharing a panel between people, device health and public
sign-up, and all four stay out — device health particularly, since "last seen"
is the feature that quietly turns a subscribe-only device into one that phones
home.

**It looks like HockeyTrack**, per §5.1 of that spec: the same typography,
palette and static-files-on-CloudFront shape. It is the same project and should
read as one.

### 10.1 Tokens in the browser

> **Amended 2026-09-13** by `2026-09-13-google-sign-in-design.md`. The hosted
> UI now hands sign-in to Google, so a silent re-authentication passes through
> Google's session as well as Cognito's. Nothing else in this section changes.

This deserves its own treatment because it is where a security-minded reader
will look hardest.

Access and ID tokens are held **in memory only**, never in `localStorage` or
`sessionStorage`, so a token does not survive a tab close and is not readable
by any script that manages to run on the page. The refresh token is left to
Cognito's hosted UI session cookie rather than stored by this application. The
practical cost is that a page refresh requires a silent re-authentication
round-trip; that is the right trade for a site whose entire job is controlling
someone's hardware.

The CSP already deployed on the distribution permits `connect-src` to exactly
the admin API and the Cognito endpoint, `frame-ancestors 'none'`, and no inline
script.

## 11. Testing

**Go, headless, in CI.** CSR validation gets the widest coverage, because it is
the one input an anonymous stranger fully controls: malformed PEM, over the
size cap, wrong key type, an oversized RSA key. Then the state machine, with
emphasis on the transitions that must fail — claiming twice, claiming an
expired row, collecting twice, collecting with a wrong token. Plus an assertion
that rows are written with their TTL set, since a TTL nobody tests is a TTL
that is silently absent.

**The 404-never-403 property extends here.** A wrong collection token and a
nonexistent one must be indistinguishable, exactly as the admin API already
treats an unowned device.

**Python, headless.** That the keypair is generated once and reused; the
backoff schedule; which screen each failure state produces; and that a
half-written config file is impossible.

**Not testable in CI**, and listed so it is not quietly skipped: a real Cognito
token driving a real claim, a real certificate issued, and a real device
connecting to IoT with it. That is a hardware check alongside the image work's
H1–H7.

## 12. What a security review should attack

In the order they matter:

1. **Can a certificate be obtained without an authenticated, invited owner?**
   Every other property here is decoration if this one fails.
2. **Can the enrollment role attach anything other than the device policy?**
   See §8.
3. **Is anything trusted from the CSR?** See §8.
4. **Does seeing the screen yield the device's identity?** The collection token
   exists to make the answer no; try to reach a certificate knowing only a code.
5. **Can a pre-bound code be claimed by anybody but its owner?** Try claiming
   one as a different invited user, and try defeating the comparison with case,
   whitespace, a plus-addressed variant, or a Unicode homoglyph of the owner's
   address.
6. **Does a table dump yield anything usable?** Both secrets are hashed; check
   that raw values never reach an item, a log line, or an error message.

## 13. Dependencies and out of scope

**Depends on:** SCO-24 (revoke on unbind) — the recovery path in §7.1 requires
it. SCO-23 (protect the devices table) becomes materially more important once
other people's panels depend on that row surviving.

**Out of scope:** public sign-up; device health and last-seen; sharing a panel
between several people; brightness and display settings; a mobile app; WAF
(§6). The image build and publication is sub-project B2; the update channel is
sub-project C.

## 14. Implementation plans

One spec, three plans, so that certificate minting does not share a review
surface with a game picker:

1. **Enrollment backend** — the table, the second Lambda and its role, the two
   endpoints, CSR validation, certificate issuance, alarms.
2. **Device first boot** — key generation, the enrollment client, the three
   screens, atomic config write.
3. **The site** — Cognito sign-in, the claim page, and the v1 panel controls.

Plan 1 and plan 2 can be built in either order against an agreed interface.
Plan 3 needs plan 1.
