# Scoreboard admin site — design

*2026-09-07. Status: draft for review. Ticket: SCO-10, epic SCO-9.*

A website where the owner of a scoreboard chooses which game it follows, and
where more than one person can own a scoreboard.

## 1. The problem, stated precisely

The device picks its own game today: two optional GPIO buttons cycle the day's
list, or you edit a file on the SD card. That works because there is one
device, one owner, and the owner can reach the hardware.

Three things do not exist and all three are needed:

- **Identity.** Nothing in this project distinguishes one person from another.
- **Ownership.** A certificate proves a device is genuine. It does not say
  whose it is.
- **A control path.** Devices are strictly one-way. They subscribe, receive
  and render; the IoT policy grants them no publish, and nothing can tell a
  device to do anything.

### What does *not* need to change

Game state is public. The retained documents on
`hockeytrack/games/<id>/state` carry NHL scores — not secret, not per-user.
Every device can keep subscribing to any game's state, and the reducer, the
today Lambda and the data path are untouched by this epic.

**Only control needs authorization: who may retarget whose device.** Saying
that plainly is worth a paragraph, because the instinct on hearing
"multi-user" is to make the whole pipeline tenant-aware, and here that would
be pure cost.

## 2. Decision: build for multiple users now

The alternative — a single-owner page with access controlled by not sharing
the URL — is genuinely cheaper and would work today. It is rejected because
the request was explicitly "I and future users", and because the saving is
smaller than it looks: with a hosted sign-in page, identity is roughly a day's
work, while retrofitting ownership onto a system that assumed one owner means
unpicking every authorization decision made without it.

Cost is not a factor either way. Cognito's free tier covers 50,000 monthly
active users; this will have single digits.

## 3. Architecture

```
   browser ──HTTPS──▶ CloudFront + S3   (static page, no secrets)
      │
      │ JWT (Cognito hosted UI)
      ▼
   API (Lambda + Function URL or API Gateway)
      │  authorizes: does this user own this device?
      ├──▶ DynamoDB  scoreboard-devices   (ownership)
      └──▶ IoT Core  publish retained to scoreboard/<thing>/config
                                  │
                                  ▼
                            the device (subscribes; still publishes nothing)
```

**The browser never gets IoT credentials.** It holds a Cognito JWT and talks
only to the API; the API holds the single IAM role permitted to publish
config, and enforces ownership before it does. The alternative — federating
Cognito identities into IoT policies with policy variables — is a legitimate
AWS pattern but pushes authorization into a policy document, where it is
harder to read, harder to test and impossible to unit-test. A Lambda that
checks a DynamoDB row is plainer.

### 3.1 Identity — Cognito user pool, hosted UI

No custom sign-in pages, no password handling of our own. The hosted UI is
ugly but free, correct, and supports the account recovery flows that are
tedious and unrewarding to build.

Sign-up is **invite-only in v1**: the pool is closed to self-registration and
users are created by the administrator. This project hands panels to family,
not to the public, and an open sign-up form on a hobby project is an
invitation to abuse it.

### 3.2 Ownership — a DynamoDB table, not thing attributes

`scoreboard-devices`, partition key `thingName`, with an `owner` attribute
holding the Cognito subject and a global secondary index on `owner` so
"list my devices" is one query.

The tempting alternative is to store the owner as an AWS IoT *thing
attribute*, which needs no new store. Rejected: querying things by attribute
requires AWS IoT fleet indexing, which is a paid feature billed per index
update, and the query is less direct than a GSI. This project already has the
DynamoDB idiom in `internal/gamestore`, so a second small table costs almost
nothing to build and nothing to learn.

The row also holds a display name the owner can set, so the site can say
"Living room" rather than a thing name.

### 3.3 Pairing — a code on the screen

The obvious way to bind a device to a person is the one most IoT products
cannot use: **this device has a 1920×480 display.**

At first boot, before it is claimed, the device shows a short pairing code.
The owner signs in, types the code, and the API binds that thing to their
Cognito subject. This is the Chromecast and Apple TV flow, and it works here
for free because the screen already exists and is enormous.

The code is derived from the thing name rather than generated by the device,
so that **the device still never publishes anything**: provisioning gives each
thing a random suffix, and that suffix is the pairing code. The server can
resolve it; the device merely displays what it already knows.

Guessing is the obvious attack. Mitigations: the code is only useful while a
device is unclaimed, claiming is one-time and requires an authenticated user,
attempts are rate-limited per user, and a device can be unbound only by its
current owner or the administrator. The security model is "you can see the
screen", which is the correct model for something sitting in a living room.

Relationship to SCO-8: AWS fleet provisioning's *provisioning by trusted user*
solves a different half of the same problem — how a device gets a certificate
at all without someone hand-copying a private key. Pairing and provisioning
should be designed together, and the pairing code slots into either
provisioning approach unchanged.

### 3.4 Control path — retained config messages

The API publishes `{"gameId": <id>}` to `scoreboard/<thingName>/config`,
**retained**. The device subscribes to its own topic only, scoped by the
`iot:Connection.Thing.ThingName` policy variable exactly as the existing
`iot:Connect` statement is.

Retained matters: a device that is unplugged when the game changes picks up
the current choice the moment it reconnects, which is the same property that
already makes state documents survive a power cut. It removes an entire class
of "I changed it and nothing happened".

This is SCO-11 and can be built before the rest of the site exists.

### 3.5 The game list — served by the API, not fetched by the browser

The site needs today's games. Two sources exist and one is unavailable:

- HockeyTrack publishes `https://hockeytrack.davidjdrake.com/data/schedule.json`,
  but **it serves no CORS headers** (verified 2026-09-06), so a browser on
  another origin cannot read it. Adding CORS to HockeyTrack's distribution
  would work but couples the two projects for a browser's convenience.
- The retained `hockeytrack/games/today` document already exists and is
  exactly this list, but it is MQTT and a browser cannot read it either.

So the API returns the list, reading the same schedule server-side as the
today Lambda already does. One more small endpoint, no coupling, no CORS
change in another project.

## 4. Endpoints

| Method | Path | Does |
|---|---|---|
| GET | `/api/devices` | the caller's devices, each with its current game and display name |
| POST | `/api/devices/claim` | body `{code}`; binds an unclaimed thing to the caller |
| PUT | `/api/devices/{thing}/game` | body `{gameId}`; publishes the retained config message |
| PATCH | `/api/devices/{thing}` | rename |
| DELETE | `/api/devices/{thing}` | unbind, returning the device to unclaimed |
| GET | `/api/games` | today's games |

Every path except `/api/games` authorizes on ownership before acting. A user
who does not own a thing gets 404 rather than 403, so the API does not confirm
that a thing exists.

## 5. Hosting

Static page on S3 behind CloudFront with an ACM certificate, in **this**
repository's Terraform. HockeyTrack's `terraform/site.tf` is the pattern to
copy — same idiom, separate stack, separate state.

**Decided: `scoreboard.davidjdrake.com`.** Verified available — the
`davidjdrake.com` hosted zone is `Z04202891HM5X7HAEVE8H` and holds no
`scoreboard` record today.

Note the one cross-project touchpoint this creates: both stacks write into
that shared hosted zone. HockeyTrack's stack owns the `hockeytrack` A record
and its ACM validation CNAME; this stack will own the `scoreboard` equivalents.
Different record names in one zone is fine for Terraform, and neither stack
manages the zone itself, so neither can destroy the other's records — but it
is worth knowing that the zone is the single resource the two projects share,
and that a `terraform destroy` here would remove DNS for this subdomain only.

The page is plain HTML and JavaScript. It has one job — list devices, list
games, set a game — and does not merit a framework or a build step. The
existing site is written the same way and is the house style.

### 5.1 It looks like HockeyTrack, because it is the same project

**Decided: reuse the existing site's design rather than invent one.**
`hockeytrack.davidjdrake.com` already has a house style, and a scoreboard admin
site that looked like something else would read as a different product.

What that means concretely, from `site/assets/site.css` in the HockeyTrack
repository: the same custom properties (`--ice`, `--ink`, `--muted`, `--rule`,
`--blue #0033A0`, `--red #C8102E`, `--crease`), the same three families
(Barlow Condensed for display and controls, IBM Plex Sans for body, IBM Plex
Mono for figures), the same uppercase condensed buttons and 2px-bordered
panels, and the same plain HTML with no build step. Fonts are self-hosted
woff2 subsets, preloaded.

**Copy the assets; do not hotlink them.** This site is a separate origin, and
HockeyTrack's distribution serves no CORS headers (verified 2026-09-06, §3.5),
so cross-origin font and stylesheet loads would need a change over there —
coupling two projects for the sake of one file. `site.css` and the five woff2
subsets are a few kilobytes; vendor them, and note in both repositories that
they are a copy, so a later redesign is a deliberate two-repository change
rather than a silent drift.

**The countdown is already built.** `site/assets/countdown.js` is a documented,
embeddable component — `data-start`, `data-away`, `data-home`, or a `next()`
callback that rolls on to the following game — and it has the accessibility
work already done: the ticking digits are `aria-hidden`, a screen-reader
summary refreshes once a minute, and there is a pause control for WCAG 2.2.2.
Reuse it rather than writing a second clock, here and in SCO-19.

## 6. Security

- The browser holds a JWT and never AWS credentials.
- The API's IAM role may publish only to `scoreboard/*/config` — not to the
  `hockeytrack/games/*` topics the reducer owns.
- Devices gain `iot:Subscribe`/`iot:Receive` on their own config topic and
  nothing else. **Devices still publish nothing**, so a compromised device
  cannot inject anything into the system. Preserving that is deliberate; a
  status or heartbeat topic is a separate decision with a real trade.
- Sign-up is closed; users are invited.
- Ownership is checked in the API on every device-scoped call, not implied by
  possession of a thing name.

## 7. Out of scope for v1

Brightness and display settings beyond game choice; sharing one device
between several users; device health or "last seen"; any notion of an
organisation or household; sign-up open to the public; a mobile app. Each is
a reasonable v2 and none blocks the first version.

## 8. Open questions

- **Does the pairing code survive a re-provision?** If a device is re-flashed
  it gets a new thing and a new code, and the old row is orphaned. Probably
  fine — the owner unbinds and re-claims — but worth deciding rather than
  discovering.
- **Should the site show what the panel is showing?** It could subscribe to
  the same state document and mirror the board in the browser. Appealing, and
  entirely unnecessary for v1.
- **Invite mechanics.** Creating users by hand in the Cognito console is fine
  for family. It stops being fine at some size that this project may never
  reach.
